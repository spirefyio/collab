## Answers

**1. Sets up the next phase cleanly?** Yes. `embed.go`'s `//go:embed *.sql` and `Migrator.Versions()`/`Head()`/`PendingAfter()` (all driven off the source driver, `migrate.go:192-248`) pick up `0002_*.sql` with zero code changes. `internal/db` and a future `internal/store` have no import-direction conflict (store would depend on `db.NewPool`'s `*pgxpool.Pool`; nothing in `db` needs to know about `store`). One small, real friction point, not a blocker: `newTestDB`/`tableExists`/`quoteIdent` (`migrate_integration_test.go:58-117`) are `package db`-private, so `internal/store`'s own future "real Postgres, throwaway database" tests can't import them and will either duplicate ~40 lines or trigger a small extraction — correctly *not* done preemptively here, since there's only one caller today (extracting for a hypothetical second caller would itself be the kind of speculative abstraction this ecosystem treats as ballast).

**2. Layering — is `internal/db` owning both pool + migrations the right shape?** Yes, and it's not a decision this diff made: `pool.go`'s package doc ("Package db owns the Postgres connection pool and migration runner") predates this commit untouched at `ab130be`. `cmd/collab-migrate` as a second `cmd/` binary in the same module is standard idiomatic Go, and here it's closer to *required* than merely conventional: a genuinely separate module could not import `internal/db` at all under Go's own `internal/` visibility rule, so sharing `Migrator` forces the "second binary, same module" shape. The alternative (separate module) would also duplicate the `golang-migrate`/`pgx` dependency graph in a second `go.sum` that could drift from the server's — undermining the exact guarantee this code's own comments emphasize (an operator can't apply a different tree's migrations).

**3. Acquisition-grade readability — what would a staff engineer flag?** The two things a sharp reviewer pattern-matches on immediately, side by side in the same switch statement / same file: `case "down"` (`main.go:116-127`) sitting right next to `case "down-all"` (`main.go:129-136`) with no confirm check on the former; and `goto`'s `if v == 0 && !confirm` (`main.go:146`) reading as "someone only thought about the exact-zero case." Both are F1. Nothing else in the new code reads as sloppy — the `Migrator` doc-comments are unusually precise (I checked the `ErrShortLimit`/`os.ErrNotExist` claim at `migrate.go:119-128` against the actual `golang-migrate v4.19.1` source, branch for branch, and it's exactly right), and the type doc-comment's "construct with NewMigrator" (`migrate.go:34`) technically undersells the deliberate, tested source-only construction path (`&Migrator{src: ...}`, used in `migrate_test.go:73` and `migrate_integration_test.go:442`) — worth a one-line doc addendum, not worth listing as a finding on its own.

**4. One image, two binaries — right call?** Yes, for this product's actual deployment story. The two binaries are two `go build` invocations sharing the same layer-cached `go mod download` (`Dockerfile:12-13`); a separate migration image would mean a second CI build/push/scan artifact per release for a binary that's a few MB and changes in lockstep with the server anyway. It also removes the real risk a split image introduces: a migrate image built from a different commit than the server it's meant to recover, silently invalidating the "an operator cannot accidentally apply a different tree's migrations" guarantee this diff is built around. An init-container is the wrong shape for a different reason: it fits the *forward* boot-time path this product already solved in-process (`cmd/relay` calling `db.RunUp`, advisory-locked so concurrent replicas are safe — verified against the real pgx driver, `pg_advisory_lock`, blocking). The new verbs (`down`/`goto`/`force`) are human-initiated, ad hoc, and must never run unconditionally on every pod start the way an init container would — the k8s-native analogue for these is a one-off Job/`kubectl exec` overriding `command` against the *same* image, which is exactly what the compose `--entrypoint` override already demonstrates; a second image would need to be built to back that Job anyway, for zero benefit.

**5. `COLLAB_DATABASE_URL` coupling on the destructive verbs — acceptable?** No — this is F2. The flexibility itself (same targets reach staging/prod) is a legitimate, stated design goal; what's missing is any on-screen confirmation of *which* database is about to be hit at the moment the destructive command actually fires. Minimal fix: echo the redacted resolved URL unconditionally before the `$(MIGRATE)` call in `db-down`, `db-down-all`, `db-goto`, `db-force`, `db-reset` — reusing `net/url.URL.Redacted()`, already present one layer down in this same diff.

README CORRECTION block — right way to carry a retraction?** Directionally yes, and it's a stronger execution than most: it edits the exact site that carried the false claim (`README.md`'s Architecture §2, which used to list `/auth`, `/teams`, `/workspaces`, `/invites`), it's dated, it quotes the false claim verbatim rather than paraphrasing it away, and it cites concrete evidence (`internal/api/teams.go`, `migrations/0001_init.up.sql`) rather than just asserting. That matches the standing requirement (retract at the site, not only in conversation/commit message) better than a silent rewrite would have, and it's consistent with this org's own demonstrated practice (the root ecosystem `CLAUDE.md`'s own "Provenance — RECONCILED" block at the top of that file does the same thing). The execution has the two concrete flaws in F3: the "empty" imprecision, and the duplicated owed-inventory that will drift once the store actually lands and only one of the two copies gets updated.

**7. What's missing for this to be a complete operator surface?**
- **F1 and F2 above** — the two confirmation-gate defects are the most load-bearing gaps: they sit directly in the verbs this PR exists to ship.
- **F4** — no CI runs any of this. Matters most because this specific PR is the one that made "irreversible" load-bearing.
