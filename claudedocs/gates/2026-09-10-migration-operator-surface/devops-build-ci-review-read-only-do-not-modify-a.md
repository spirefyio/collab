## 2. THE PRODUCTION FOOTGUN

Real, and worse in one respect than the prompt's framing suggests. **CONFIRMED-BY-MEASUREMENT** — I ran `make -n` (dry-run, prints the resolved command, executes nothing) from a copy of the Makefile with `COLLAB_DATABASE_URL` exported to a fake production URL:

```
$ COLLAB_DATABASE_URL='postgres://prod_admin:S3cr3t!@prod-db.internal.example.com:5432/collab_production?sslmode=require&application_name=collab-server' make -n db-down N=1
...
bin/collab-migrate -url 'postgres://prod_admin:S3cr3t!@prod-db.internal.example.com:5432/collab_production?...' down 1
```

- **CRITICAL** — server/Makefile:100-102 (`db-down`) and :109-111 (`db-goto`, any non-zero `V`): **zero confirmation of any kind**, at either layer. `db-down` requires only that `N` be non-empty (server/Makefile:101); the CLI's own `down` case (server/cmd/collab-migrate/main.go:116-127) has no `!confirm` check either — only `down-all` does (line 130). So an operator who has `COLLAB_DATABASE_URL` exported in the same shell for any legitimate reason (a one-off prod debug session, a sourced `.env.production`, a bastion profile) and who types `make db-down N=1` or `make db-goto V=<n>` out of local-dev habit runs real destructive `.down.sql` against production **immediately, with no prompt at all**.
- **HIGH** — server/Makefile:104-106 (`db-down-all`), :125-128 (`db-reset`), :114-117 (`db-force`): gated by `CONFIRM=yes`, but that gate is (a) contentless — it never names the resolved database — and (b) **is** the value that becomes the CLI's `-yes` flag (measured: the moment `CONFIRM=yes` is given, the printed command is `... -yes down-all` against whatever URL COLLAB_DATABASE_URL resolved to). Directly answering the prompt's question: **the CLI's own `-yes` gate provides no independent protection here** — it is satisfied automatically and silently by the Makefile wrapper. Two nominally-independent confirmations collapse into one blind token.

Minimal fix, in order of value: (1) give `db-down`/`db-goto` a `CONFIRM=yes` guard identical to the others — closes the CRITICAL zero-gate case cheaply; (2) make every destructive guard's refusal message print the resolved `$(DB_URL)` host (not the full URL/credentials) so a human actually sees what they're about to hit, consistently — right now only `db-reset` does this, by accident, and only on the failure path; (3) the durable fix is separating "which DB does this target" from a single shared env var — e.g. requiring `-url` explicitly for destructive verbs, or a distinct `COLLAB_MIGRATE_CONFIRM_HOST=<hostname>` double-keyed check — but that's a design change beyond this diff's scope, not a one-line patch.
